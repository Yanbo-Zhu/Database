## 3.1 **Strict 2PL 的定义**

Strict 2PL 的要求：
- 加锁阶段（growing phase）和释放锁阶段（shrinking phase）分开。
- 所有排他锁（X锁）必须保留到事务提交（或中止）之后才能释放。  
  也就是说，事务不能在 commit 前 unlock 任何 X 锁。

如果 某个数据写之后， 还被这个transcation 或者 其他 transcation访问这就违法 违反 strict. 因为 按照 strict PL , 数据写之后 X锁还不能去除， 要等到 commit 之后， shrinking截断 才能去除 X 锁。 
X锁还不能去除的时候， read 操作在 stirct-2PL 是不被允许的。  stirct-2PL中 写锁必须保持到 commit ， 在此之前，任何事务不能读。 

只有等 X锁取出后 才能 read, 
如果没有x锁， 只是之前加了 shareable 锁 则， 后取读同一个元素 是 被 stirct-2PL 允许的 

## 3.2 分析



**1. 原题 S1 的操作序列**

`[ S_1: r_2(C); w_3(B); w_3(B); w_2(C); w_1(C); r_1(B); r_1(C); r_2(A) ]`


，然后构造了一个加锁版本（带 lock/unlock 的调度）来说明：

👉 这个 schedule 是 2PL-compatible
👉 但 不是 strict 2PL-compatible

---

**2. 题目给出的"2PL-compatible"的加锁版**

> S2(C) R2(C) X3(B) W3(B) W3(B) X2(C) W2(C) S2(A) U2(C) X1(C) W1(C) U3(B) S1(B) R1(B) R1(C) R2(A) U2(A) U1(C) U1(B)

我们对应一下事务与操作：

- **T2**: S2(C) → R2(C) → X2(C) → W2(C) → S2(A) → U2(C) → R2(A) → U2(A)  
  在释放 U2(C) 后（解锁 exclusive lock on C），还在执行 R2(A)。  
- **T3**: X3(B) → W3(B) → W3(B) → U3(B)
- **T1**: X1(C) → W1(C) → S1(B) → R1(B) → R1(C) → U1(C) → U1(B)

注意 U3(B) 发生在 W1(C) 之前，W1(C) 在 X1(C) 后。


**哪里违反 Strict 2PL**

在给出的加锁顺序中：
T2 拿到了 X2(C)（排他锁），执行 W2(C)，之后 **U2(C)**（释放 X 锁）。  
U2(C) 之后 T2 又执行了 R2(A)（这条操作在 schedule 里确实在 r2(A)），然后 U2(A) 才完成事务。

Strict 2PL 要求所有排他锁（X 锁）保留到事务提交后释放。 如果这里 T2 在 r_2(A) 之前就释放了 X2(C)，显然违反 Strict 2PL。
但为什么不能换个顺序，比如最后 unlock C 在 commit 时？ 因为普通 2PL 允许这样，（因为释放 C 的 X 锁之后，T2 没有再申请 C 的锁，而且它确实在 shrinking phase） ， 但 Strict 2PL 禁止。

这意味着 **T2 在 commit 前释放了 C 的排他锁**，这是 Strict 2PL 不允许的，因为在 Strict 2PL 中，X 锁必须到事务结束后才能释放（通常与 commit 一起）。
